# 格优 AI 生命礼仪经营 OS 1.0 产品方案

版本：V1.0 范围稿
日期：2026年9月28日
用途：产品评审、研发估算、试点准备与验收。

## 1 产品定位与目标

面向当地生命礼仪服务代理及其业务员，提供 H5 经营工具：以代理实际可提供的商品和服务为基础，结合预置地区习俗与客户需求，由 AI 生成套餐，经业务员与客户确认后形成最终报价，并将客户、报价、跟进情况汇总给代理老板。

1.0 优先验证业务员是否能独立完成谈单报价、老板是否能看到可信的业务进展。讣告及花圈展示帮助客户联系当地代理，交易、付款和履约在线下完成。

## 2 方案依据与决定状态

依据：原《第一阶段产品共建任务书 0928—1110》、[会议纪要](https://zcnnps73daj1.feishu.cn/docx/ELE3dOflyoRJnCx685DcmpyJndf)，以及本次对话后续决定。对话中的最新决定优先于原文件及会议摘要。

### 已确认范围

- 交付 H5。
- 套餐由 AI 动态生成，商品来源为代理选用的格优商品、代理自有商品和服务项目；不是单纯匹配固定套餐。
- 试点地区习俗先统一预置，不开发代理自行维护习俗的后台。
- 有商品维护权限的人员可以维护本代理商品，不限定只有老板。
- 套餐与客户确认后生成最终报价单。
- 客户由录入人默认负责，老板可转交；同代理相同电话提示重复，不自动合并。
- 老板看板必须有，只看能确定的数据，不看营业额。
- 独立 AI 工具仅保留遗像修复；核心 AI 谈单、套餐生成仍保留。
- 花圈不做线上支付，展示所属代理的微信二维码和电话，由客户线下联系、付款，代理线下履约。
- 格优查看代理数据后置。

### 本稿为快速落地提出的实现建议

业务员代为记录客户确认、轻量角色授权、人工标记成交、平台维护首批数据、公开页面访问方式及下述页面结构，均为实现建议，不代表新增的客户承诺。研发评审可调整实现方式，但应保留已确认的业务结果与数据边界。

## 3 用户与使用边界

| 用户 | 主要任务 | 数据范围 |
|---|---|---|
| 代理老板 | 查看经营情况、管理本店人员、转交客户、配置权限 | 本代理全部业务数据 |
| 代理业务员 | 维护客户、生成方案、沟通确认、出报价、跟进 | 默认本人负责的客户及关联业务 |
| 商品维护人员 | 维护商品、服务和本店价格 | 本代理商品库；可由老板或业务员兼任 |
| 客户及亲友 | 查看分享报价、讣告、花圈，联系代理 | 被分享的对外内容，无管理后台权限 |
| 平台维护人员 | 开通代理、维护格优公共商品、预置习俗 | 必要配置功能；不提供跨代理经营查询页面 |

H5 包括登录后的代理工作台及公开分享页面。商品维护权不自动赋予客户明细或老板看板访问权。平台维护能力不等于格优获得代理经营数据查看权限。

## 4 核心业务流程

### 4.1 谈单与最终报价

1. 建立或选择客户，确认负责人。
2. 填写服务地区、预算、偏好及本次特殊要求。
3. 系统读取代理启用的商品和服务、对应地区的习俗规则。
4. AI 生成套餐草稿，包括项目、数量、推荐理由、需确认事项。
5. 系统校验项目与价格，计算金额；业务员与客户沟通，增删、替换或调整。
6. 客户确认后，业务员记录确认结果，再生成最终报价单。
7. 分享或打印报价，记录跟进和成交状态。

首版建议不做电子签署或客户在线确认按钮。确认记录包含操作人、确认时间、确认版本及可选备注；此记录是业务记录，不等同电子签约。

最终报价生成不自动标记成交。客户确认后又调整项目或价格时，应产生新版本、重新确认；历史报价保留。

### 4.2 老板查看与管理

老板查看本店看板 → 点击指标进入明细 → 查看客户、负责人及最近跟进 → 必要时转交客户或推动跟进。

### 4.3 讣告与花圈联系

员工填写固定模板 → 关联本代理并预览发布 → 分享讣告 → 亲友浏览代理启用的花圈 → 查看微信二维码或拨打电话 → 在线下沟通购买。

1.0 不提交购买订单，不收款，不记录物流，不执行结算。联系点击仅表示联系意向，不能推断购买成功。

### 4.4 遗像修复

上传照片 → 提交修复 → 查看处理中、成功或失败状态 → 预览并下载。失败可重试，生成内容由使用者检查后使用，不自动发布到讣告。

## 5 功能要求及验收要点

| 模块 | 1.0 功能 | 验收要点 |
|---|---|---|
| 账号与权限 | 登录、代理归属、老板与业务员基础权限、商品维护授权 | 不同代理隔离；无权限人员不能维护商品或查看老板数据 |
| 代理资料 | 名称、服务地区、联系电话、微信二维码 | 分享内容展示正确代理；缺少联系方式时阻止发布花圈联系页面 |
| 商品与服务 | 选用格优商品、添加自有商品及服务；维护名称、说明、图片、单位、价格、启停 | 已停用项目不进入新 AI 套餐；单位与价格完整；服务按项目报价，不扩展调度 |
| 地区习俗 | 统一预置适用地区、必备项目、可选习俗、禁忌、确认人、版本 | 命中正确地区；未覆盖地区提示人工确认，不自动编造 |
| AI 套餐 | 采集需求、组合现有项目、提供讲解和缺项提醒 | 输出仅引用代理有效项目；金额由系统计算；生成失败可重试或人工组单 |
| 套餐调整 | 增删、替换、数量与单次报价调整 | 必备项目被删除时提醒；人工调整可追溯；不默默修改商品库 |
| 最终报价 | 客户确认记录、报价编号与版本、分享、打印 | 未确认草稿不能作为最终报价；历史快照不受商品调价影响；打印包含项目、数量、单位、单价、合计、代理联系信息 |
| 客户跟进 | 联系方式、负责人、需求、阶段、关联方案报价、跟进记录、转交 | 同电话提示重复；转交记录可追溯；客户阶段与报价状态分别管理 |
| 老板看板 | 本店客户、报价、跟进、人工成交、业务员表现 | 指标可进入明细，口径一致，不展示收入、利润或推测性指标 |
| 遗像修复 | 上传、处理状态、预览、下载、失败重试 | 可完成真实修复流程；不同代理不能访问彼此的私有照片 |
| 讣告 | 少量固定模板、填写、预览、发布、分享、撤回 | 必填信息完整；分享内容只展示已发布信息；撤回后公开页不可继续展示正文 |
| 花圈展示 | 商品图片、规格、展示价格、二维码、拨号 | 联系的是讣告所属代理；页面不出现下单、支付或结算入口 |

“代理拥有的商品”在首版表示代理确认可提供的项目，不表示实时库存；库存数量、锁库存、采购、补货均不建设。

## 6 AI 生成与报价控制

AI 使用的输入包括客户需求、代理商品及服务清单、预置地区习俗。不接入未确认的自动民俗采集，不为首版建设复杂知识库。

- AI 输出项目标识、数量、说明与提醒。后台验证项目属于当前代理且启用。
- 默认单价从代理商品库读取。系统按统一的金额精度计算行金额和总额，AI 文本不能覆盖计算结果。
- 超预算、缺价格、缺必备项目时标记待处理。不能虚构新商品、把缺价格当零元或用其他地区习俗直接补齐。
- 单次人工改价保存为当前方案调整，不回写商品默认价。
- 被确认的方案版本与最终报价快照绑定。新调整不覆盖旧报价链接所指向的历史版本。
- AI 不可用时支持人工从商品库组合方案，保障基本谈单可继续。

## 7 老板看板口径

建议提供今日、本月、自定义时间。为避免时间口径混乱，现状指标与期间事件指标分组显示。

| 指标 | 定义与时间口径 |
|---|---|
| 客户总数、各阶段客户数 | 当前本店未归档客户现状，明确标注“当前” |
| 新增客户数 | 所选期间创建的客户数 |
| 方案客户数 | 所选期间至少保存过一次套餐草稿的去重客户数 |
| 最终报价客户数 | 所选期间至少生成过一份最终报价的去重客户数 |
| 报价单数量 | 所选期间新建的最终报价主单数量；同一报价的修订不增加主单数 |
| 跟进客户数 | 所选期间新增过跟进记录的去重客户数 |
| 人工确认成交数 | 所选期间人工确认且当前仍有效的服务成交数，历史客户级成交单独标注未关联，不自动分配逝者 |
| 业务员表现 | 分别展示当前负责客户数，以及期间本人执行的新增、跟进、报价、成交记录；客户转交不改写历史操作归属 |
| 页面浏览与联系点击 | 按代理统计有效页面加载、展示二维码和拨号点击事件；不称为实际联系人数、订单数或成交数 |

金额只用于套餐和报价，不进入营业收入统计。看板首版不展示成交转化率，避免在分母、跨期成交尚未明确时产生误导。

## 8 首版页面结构

- 工作台：业务员快捷入口；老板可进入本店看板和明细。
- 客户：列表、详情、跟进、负责人转交、关联方案和报价。
- AI 谈单：需求输入、套餐草稿、修改核价、确认、最终报价。
- 商品库：格优商品选用、本店商品及服务、编辑、启停。
- 讣告：列表、固定模板编辑、预览分享、撤回。
- 遗像修复：上传、任务状态、结果。
- 设置：本店信息、地区、联系二维码与电话、人员权限。
- 对外 H5：最终报价页、讣告页、花圈展示及联系页。

导航可以合并，但功能与权限边界应保持清晰。首版优先手机使用，打印报价在电脑浏览器同样可用。

## 9 不进入 1.0 的范围

格优跨代理数据看板；花圈线上订单、支付、退款、履约工单、结算；采购库存；完整 ERP、财务、排班和车辆调度；录音整理；灵堂效果图；AI 挽联生成；数字人、视频、海报；代理自助习俗维护；复杂知识库；电子签约；自动民俗采集。

格优公共商品管理、代理开通和地区内容预置属于必要维护能力，可先通过受控后台或导入完成，不要求开发完整平台运营系统。

## 10 试点与交付计划

原任务书的 10月10日试点、10月30日迭代、11月10日首发会继续作为目标节点，不作为已验证工期承诺。研发需依据本方案、已有系统和实际工时重新估算。

建议保留至少5家代理试点、每家至少3次有效谈单流程、累计至少15次、形成问题清单的目标，最终以试点名单及双方验收约定为准。一次有效谈单指真实需求完成方案保存、客户确认、最终报价及跟进记录，不以重复生成 AI 内容充数。

| 阶段 | 产出 | 进入下一阶段的条件 |
|---|---|---|
| 范围与资料准备 | 功能清单、权限表、首批商品服务、地区习俗、试点名单 | 核心资料完整，确认人明确，研发完成估算 |
| 核心链路实现 | 登录、商品库、AI 套餐、确认与报价、客户跟进 | 业务员可独立走通一次谈单流程 |
| 首版整体验收 | 看板、遗像修复、讣告与花圈联系、权限检查 | 看板可核对，公开页面归属正确，无阻断核心流程的问题 |
| 真实试点 | 使用记录、问题清单、访谈反馈 | 达到约定使用目标，确定下一版取舍 |

## 完整殡葬服务周期与后续事项（2026-09-28，用户确认）

客户主进度采用：接洽登记 → 治丧筹备 → 告别仪式 → 安葬安置 → 后续关怀 → 服务结束。销售结果单独记录，安葬完成或单项事项完成均不自动结束客户服务。

每位客户维护离世/告别/安葬关键日期，并可添加告别、安葬、首次回访、百日纪念、周年纪念、祭扫及自定义事项。上述仅为节点名称建议，日期必须按地区口径与家属意愿人工核定，以公历日期保存，不默认推算宗教、农历或地方礼俗。

用户确认1.0方式：先提醒业务员，业务员确认后分享给家属。事项字段包含日期、事项清单和家属消息；状态为待确认、待发送、已发送、已完成或已取消。编辑后重新待确认；取消或待确认期间分享页不可访问。

### 2026-09-29 全局关联修正（当前规则）

- 本原型每位逝者对应一条本次服务，服务标识为客户ID＋逝者ID；谈单、套餐、报价继承该关联，收款随报价归属。新建谈单必须选定逝者，报价展示服务对象快照。旧未关联报价保留并标注，不自动猜测归属，新确认需重新明确对象。
- 成交状态移到本次服务独立记录；客户顶部为汇总。旧客户成交只作为历史记录，不解锁新服务。人员确认本次成交后，再确认进入筹备，仍不强制收款。看板成交数按服务统计并包含明确标注的历史成交。
- 所有阶段入口统一校验：推进需本次服务成交；跨阶段、回退需填写原因并写入跟进记录；结束前必须完成或取消待办并处理复核。撤销成交需先说明原因退回接洽登记。
- 制作、确认、发布待办仅跟随当前讣告 activeNoticeId。保存新草稿切换当前讣告，编辑旧讣告不会抢占当前关联，需明确点击“设为当前服务讣告”才切换；旧已发布内容不能替代新草稿的完成证据；撤回当前不会回退到旧版。旧公开页保留至人员主动撤回，不自动替换公开内容。
- 讣告保存草稿不会写服务日期。人员点击“确认同步告别日期到服务安排”并确认后，保存草稿并显式同步；若已发布，会提示暂时撤下。发布必须已确认服务告别日期且一致。改期沿用原来的待核对机制，不静默改动既有安排。
